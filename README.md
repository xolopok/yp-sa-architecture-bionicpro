# Спринт 9. BionicPRO

## Исходные данные

Кейс: компания BionicPRO производит и продаёт бионические протезы. Протез состоит из миодатчиков, чипа ESP32 с программой распознавания движений, актуаторов, батареи, системы управления батареей и корпуса. Скорость реагирования -- до 100 мс; миосигналы уникальны для пользователя и меняются со временем, поэтому протез донастраивается через приложение на Android/iOS. Телеметрия с протезов собирается в реальном времени через 4G-модуль.

IT-система: программа в чипе протеза, приложение для донастройки, интернет-магазин, CRM.

### Проблемы

- **П1.** Утечка персональных данных через уязвимость в SSO (OAuth 2.0 Code Grant в Keycloak): скачаны данные пользователей по всем протезам, судебные иски, приоритет -- усиление безопасности.
- **П2.** Пользователи требуют возможность скачать отчёт о работе своего протеза (обещано для Android-приложения).
- **П3.** Огромный объём данных в единственной БД PostgreSQL: деградация производительности, индексы не помогли.
- **П4.** Выход на новые рынки: требования законодательства к хранению медицинских и авторизационных данных отличаются по странам.

### Цели бизнеса

- Злоумышленники не должны использовать уязвимость SSO.
- Пользователь может скачать данные о работе протеза в виде отчёта: выгрузка из CRM в ClickHouse, отдельное приложение-отчёт из нескольких источников (CRM и DB).
- Пользователь имеет доступ только к отчётам о своих протезах.

## Задания

### Задание 1. Повышение безопасности системы

- [x] Задача 1. `Task1/` -- drawio-схема управления учётными данными пользователя: унификация доступа через запрос учётных записей из внешнего источника в стране представительства (без нарушения принципов локального хранения персональных и медицинских данных); схема работы с access/refresh-токенами, при которой токены IdP не передаются фронтенду; поддержка аутентификации через внешние удостоверяющие службы разных стран.
- [x] Задача 2. Замена Code Grant на PKCE: фронтенд (`frontend/src/App.tsx`, `frontend/src/components/ReportPage.tsx`) и Keycloak (`keycloak/realm-export.json`).

### Задание 2. Разработка сервиса отчётов

- [ ] Задача 1. `Task2/` -- drawio-схема архитектуры: ETL-процесс на Apache Airflow, объединяющий данные с датчиков и данные CRM, витрина отчётности в OLAP БД (ClickHouse), бэкенд-сервис API из исходной архитектуры.
- [ ] Задача 2. Airflow DAG в отдельной папке (`airflow/`): ETL из CRM в OLAP, витрина (телеметрия + данные о клиентах из CRM, сгруппированные по клиентам, структура под быстрый доступ по пользователю), расписание запуска.
- [ ] Задача 3. Бэкенд API `reports` в `backend/`: эндпоинт `GET /reports` возвращает отчёт по заданному пользователю из ClickHouse без сложных вычислений в реальном времени.
- [ ] Задача 4. Ограничение доступа к эндпоинту отчётности (`backend/`): отчёт доступен только о себе и только аутентифицированному пользователю.
- [ ] Задача 5. Кнопка получения отчёта в UI (`frontend/src/components/ReportPage.tsx`) с вызовом эндпоинта.

### Проверка перед сдачей

- UI-код вызывает API генерации отчётов.
- Неаутентифицированный пользователь не может получить отчёт.
- Авторизованный пользователь получает только собственный отчёт.
- Отчёт генерируется по запросу пользователя из OLAP: приложение отправляет запросы в ClickHouse.
- Генерация отчётов только за период, который уже обработан Airflow: запрос данных, которых ещё нет в OLAP, обрабатывается корректно.
